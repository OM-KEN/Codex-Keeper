# 开发说明

## 构建与运行

需要 Apple Silicon Mac 和 Xcode Command Line Tools（`xcode-select --install`）。在项目根目录运行：

```sh
./run-tests.sh
./build.sh
open .build/CodexKeeper.app
```

原生 Swift / SwiftUI / AppKit 应用，无 xcodeproj。`build.sh` 的 SOURCES 显式列出 Swift 文件；新增源文件要更新列表。版本来自 `VERSION`，部署版本来自 `Info.plist`。

界面支持简体中文与英语，跟随 macOS 为应用选择的语言。中文文案作为 `L10n` 的回退键，英文位于 `en.lproj/Localizable.strings`；新增面向用户的文字须补齐英文键值。`build.sh` 将两种语言资源复制入 App，并把它们计入构建指纹。设置中的默认续跑内容不可编辑，按当前语言发送“继续”或“Continue”；选择自定义后通过弹窗保存内容，切回默认时保留自定义文字以便再次选择。旧偏好没有明确模式时，保存的内置默认值按默认处理，其他非空内容和已标记的自定义值按自定义处理；旧版手动改回与默认值完全相同的文字无法区分，按默认值处理。

默认使用临时签名，避免安装包包含个人开发者证书中的邮箱和身份标识，因此其他开发者不需要作者证书也能编译。如需证书签名，可显式设置 `CODE_SIGN_IDENTITY`，该证书的公开身份信息会随应用分发。构建先在临时目录完成并验证签名，再替换目标应用；运行中的目标应用不会被覆盖。使用 `BUILD_DIR=.build/candidate ./build.sh` 可以保留当前运行版本。

应用图标源文件是根目录的 `Codex Keeper.jpg`，纳入构建指纹并原样保留。构建时用系统 `sips` 和 `iconutil` 在临时目录生成标准十种尺寸，再将 `AppIcon.icns` 放入应用资源，由 `CFBundleIconFile` 引用；生成资源不提交。首次引导显示同一应用图标，菜单栏仍使用表示运行状态的系统符号。

本机通知图标核验（2026-10-08，macOS 26.6.2）：Finder 图标正常、通知设置仍显示占位图标的原因是旧图标索引缓存。备份并重建当前用户缓存目录（`getconf DARWIN_USER_CACHE_DIR`）下的 `com.apple.iconservices/store.index`，确认当前用户的 `iconservicesagent` 实际退出并重新载入后，通知设置恢复正确图标。应用图标资源、版本、通知权限和记录保持原样；这是本机修复，应用不会自动重建系统缓存。验证用的应用副本结束后取消登记，备份以 ZIP 保存，避免旧 `.app` 副本参与应用解析。

## 适用范围与兼容性

- **平台**：Apple Silicon、macOS 13+。部署下限与验证机器上官方 Codex 应用声明的 13.0 一致；已通过该目标编译，尚未在 macOS 13 真机验证。macOS 13 使用原生编辑器样式，14+ 使用 plain 样式。
- **已核验客户端**：2026-10-09，本机 Codex 26.1002.52244（13536），内置 CLI 0.162.0-alpha.2；已确认 CLI 定位、只读查询、无提示词启动及计划保活的真实完成。此前核验过 Codex 26.924.22138 / CLI 0.158.0-alpha.2.1 和 Codex 26.908.70816（9275）/ CLI 0.154.0-alpha.6.2。官方应用包名为 ChatGPT.app，bundle ID 为 com.openai.codex。
- **账户**：ChatGPT 登录；API key 和其他登录方式不支持。账户 ID 优先使用额度响应，缺失时核对本地认证文件的稳定 account_id；冲突、缺失或读中变化均暂停自动操作，不以邮箱代替身份。
- **安装路径**：优先运行中的官方 Codex 应用，其次系统及用户 Applications 中的 Codex.app / ChatGPT.app，再检查绝对 PATH 和常用 Homebrew 路径。每个应用包先查新版内置 CLI `Contents/Resources/codex-cli/CodexCLI.app/Contents/MacOS/codex`，再兼容旧版 `Contents/Resources/codex`；标准安装位置不依赖 shell PATH，无须另装 CLI。
- **手动兜底**：正常设置页不显示备用路径。找不到可用的 Codex CLI 时，点击菜单中的错误提示打开独立的路径窗口，可输入或选择文件，保存后立即重试。保存前去除首尾空白并展开 `~/`，要求绝对路径指向存在且可执行的普通文件，支持文件符号链接及路径中的空格；空白输入不能提交，不执行 shell 展开或 `--version` 探测。已保存路径仍仅在自动候选不可用时使用。额度查询、保活及独立 app-server 续跑共用 `CodexLocator`，直接将路径传给进程。
- **数据目录**：统一使用 `CODEX_HOME`，未设置则为 `~/.codex`；由 Finder 启动时不会自动继承 shell 配置里的环境变量。自定义目录必须传入启动环境，且与目标 Codex 使用同一目录。
- **任务范围**：当前 Mac 的本地任务；不承诺云端、远程主机和其他操作系统。
- **故障处理**：按日志及 WAL 修改时间发现当前 `logs*.sqlite`，轮换或截断时重读。格式不兼容、已有任务却无法读取日志时暂停自动操作；发送前重新验证目标仍有同一次额度停止证据。新用户没有任何任务或日志时显示空任务列表。

官方接口用于账户、额度、模型发现和独立 app-server 续跑。桌面 IPC、rollout、日志数据库、认证和草稿文件仍含非公开兼容层，因此不能承诺支持 Codex 的所有历史与未来版本。升级 Codex 后应重新核验；无法可靠确认时停止并显示错误。

资料：[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)、[Codex 模型](https://learn.chatgpt.com/docs/models)、[Codex 应用](https://learn.chatgpt.com/docs/app)。应用网页确认 Apple Silicon 支持，macOS 13 下限来自上述安装包的 Info.plist。

### CLI 兼容性验证

人工验证可运行 `./Probes/check-cli-compatibility.sh --identity` 核对 CLI 路径、版本和 SHA-256，或使用 `--check` 检查账户/额度/模型及无提示词 TUI 启动；配置生成函数由生产保活与探针共用，覆盖全新目录与旧后台服务路径。启动通过不等于保活成功，完整结果仍从计划操作的真实日志确认。提交、推送及发布仍需维护者明确同意。

OM 的每日 Codex 更新提醒属于本机个人工具，源码和测试已于 2026-10-12 迁至仓库外；启动配置及运行数据也保存在仓库外，不纳入 Git 或 Keeper 安装包。本机位置为 `~/Library/Application Support/CodexKeeper/update-reminder/tool/`，维护说明见该目录的 `README.md`；每天 09:00 由用户 LaunchAgent 运行，不调用模型或发送 Codex 聊天消息。原高频 Codex 自动化不恢复。

## 安装包与发布

DMG 使用 Copied 的拖入 Applications 布局。打包依赖 Python 3.10+ 和 dmgbuild 1.6.7，建议装在虚拟环境中：

```sh
python3 -m venv .build/dmg-tools
.build/dmg-tools/bin/python -m pip install 'dmgbuild==1.6.7'
PYTHON=.build/dmg-tools/bin/python ./create-dmg.sh
```

输出为 `.build/CodexKeeper-<VERSION>.dmg`。默认以临时签名分发，不要求 Developer ID 或公证，也不自动使用本机个人开发者证书。`--release` 可用于发布构建，与默认构建使用同一签名策略；设置 `CODE_SIGN_IDENTITY` 可显式选择证书签名。

公开仓库为 [OM-KEN/Codex-Keeper](https://github.com/OM-KEN/Codex-Keeper)。版本来自 `VERSION`；普通修复和现有交互的局部改善发布 patch，有明显新使用场景时发布 minor，不兼容变化发布 major。各段限单个数字 0–9，超出时向前进位并将后续段归零，如 `0.1.9 → 0.2.0`、`0.9.9 → 1.0.0`；`build.sh` 拒绝多位数字。发布 tag 为 `v<VERSION>`，标题为 `Codex Keeper v<VERSION> (macOS)`，仅上传 `CodexKeeper-<VERSION>.dmg`。正文面向普通用户，优先说清使用上有什么变化；每条简短、准确，可适当轻松有趣，避免技术术语、内部实现、空泛赞美和夸大承诺。修复项点明原来的问题及改善，细节只在帮助用户理解时保留。默认流程：先只交付中文“新功能 / 修复”草稿，等待 OM 修改或明确确认；以确认的中文为准补充对应英文，再按本次授权发布。只有 OM 明确要求跳过时，才直接整理双语发布稿。最终正文按 What's New、Fixes、新功能、修复排列，同类英中内容对应，无该类变化时省略。项目采用根目录 `LICENSE` 中的 MIT 许可；`assets/NOTICE.md` 保留所复用背景和布局的许可。构建时将两者一并放入应用资源。

发布前运行回归、构建及 DMG 校验，挂载检查 Finder 背景、图标布局、App 和 Applications 链接，并记录大小及 SHA-256；发布后核对远端提交、tag、稳定版与 Latest 状态，以及唯一 DMG 资产的下载、大小和校验和。提交、推送及发布仍需维护者明确同意。另一台 Mac 的首次安装、登录读取、登录项、保活及续跑验收，以及 macOS 13 真机验证仍待完成。

未公证应用首次打开可能被系统拦截；用户确认来源后，可按 [Apple 的打开说明](https://support.apple.com/zh-cn/102445)操作。不要把开发签名描述为公证签名。

## 首次启动

新用户依次看到品牌页、保活与时间设置页、自动续跑介绍页。品牌页使用应用图标。开始时间默认 08:00，后三个计划时间即时联动，跨天标注“次日”；支持返回调整。页面整体左对齐，保留“1.”与“2.”编号，标题与正文保持清晰层级；窗口统一为紧凑宽度，高度跟随每页内容，切换时保持顶部位置。使用 AppKit 先淡出整页、调整窗口高度、再淡入新页，避免文字在尺寸变化中重新排列；减少动态效果时省略尺寸动画。返回位于左下角，下一步位于右下角，计划时间位于标签下方。最后点击“开始使用”才保存并启动菜单栏服务。完成前不会初始化额度读取或自动执行。关闭引导会退出，下次打开再次显示；完成后不再重复。已有设置的用户升级时沿用原偏好，不显示引导。

## 关于、更新与反馈

菜单中的版本号位于设置下方、退出上方，读取当前应用包的 `CFBundleShortVersionString`。点击打开可复用的 440 × 380 关于窗口，显示应用图标、名称、版本，以及分组的软件更新和支持与反馈。菜单与关于页共用同一个 `AppUpdateService`；发现新版且提醒开启时，在版本号后显示“有新版本”和绿色圆形向上箭头。

更新提醒默认开启，可在关于页关闭；关闭后停止自动检查并隐藏菜单提示与重要更新弹窗，手动检查仍可用。启动、应用激活、系统唤醒及每 15 分钟的定时器会核对检查期限：成功后间隔 24 小时，失败后间隔 1 小时。手动检查立即发起，同一时间只进行一次检查。更新检查通过独立的临时 `URLSession` 向 `https://api.github.com/repos/OM-KEN/Codex-Keeper/releases/latest` 发出一次 JSON GET，仅接受该接口的正式非预发布版本，核对 tag 与可信 HTTPS GitHub 发布页的版本一致，再按主、次、修订版本数字比较。仅可信接口的 429 或带限流证据的 403 会追加一次原有 `releases/latest` HEAD 检查，保留普通更新提示，并在 1 小时后重试元数据；相同版本可沿用已验证的重要标记，新版本不会继承未确认的标记。其他失败保留已验证的缓存。更新检查不使用 Codex 连接或发送任务消息；单请求超时 10 秒、整体资源超时 15 秒。关于页显示检查状态，发现新版后打开对应 GitHub Release，下载安装由用户完成。

更新偏好和缓存保存在应用的 `UserDefaults`：`automaticUpdateRemindersEnabled`、`appUpdateLastCheck`、`appUpdateLastCheckFailed`、`appUpdateCachedReleaseURL`、`appUpdateCachedImportantVersion`、`appUpdatePromptedImportantVersions`。重启时重新验证缓存链接，仍比当前版本新则恢复提醒；旧缓存没有重要标记时只恢复普通菜单提示。检查失败保留已发现的新版，确认已无新版或无稳定版时清除对应缓存。

重大更新由维护者手动标记，不从主版本号推断。在 Release 正文中独立放置一行 `<!-- keeper-important-update: 1.1.0 -->`，表示低于 `1.1.0` 的客户端需要重要提醒；该标记不在 GitHub 页面正文中显示。只接受唯一、规范且不高于发布版本的标记；后续普通版本沿用最近的重大版本门槛，避免错过中间版本的用户漏提醒。例如最新为 `1.1.1`、标记为 `1.1.0` 时，`1.0.x` 用户会看到前往最新版本的提醒，`1.1.0` 用户只看到普通更新入口。新的重大更新改为新的门槛值。最终双语发布稿中保留此元数据，面向用户的中文评审稿不必展示它。

每个重大门槛版本自动弹窗一次，重启和后续补丁不重复。原生信息弹窗显示“发现重要更新”，提供“前往 GitHub 更新”和“稍后”；按 Esc 选择稍后，菜单更新入口保留。菜单跟踪、其他模态窗口或 sheet、Keeper 正在执行期间延后，实际准备展示时才持久化提示记录。此功能需要客户端内置支持；加入此功能之前已分发的安装包只有原来的菜单更新提示，替换同号安装包不会让已安装用户检测到新版本。

问题反馈提供邮件和 GitHub Issue 两个入口。邮件打开系统邮件草稿，预填应用版本、macOS 版本、芯片和问题模板，收件人为 `omken.feedback@gmail.com`；GitHub 打开本仓库的 Issue 选择页。链接无法打开时显示错误。

## 现役行为

- 已接真实执行。每天以用户设定的开始时间为锚点，间隔 5 小时安排四个节点。
- Codex 桌面应用退出后，只要 Keeper 仍运行且 CLI 可用，额度查询与定时保活仍可在后台工作；续跑找不到桌面任务写入者时尝试独立 app-server 通道，不保证每次都能继续。
- 保活的开始机会为 10 分钟；首次节点按原计划，其余节点仅可依据相邻上一节点的 Keeper 成功记录顺延至真实窗口重置时间。同一账户、开始时间和时区必须一致，作为顺延依据的窗口建立延迟相对原节点最多 20 分钟；下一日首节点恢复原锚点。普通用户窗口、旧版缺少来源信息的记录、跨账户或跨计划记录不触发补偿。顺延后的机会仍只有 10 分钟，不提前发送，超过截止不补发；尝试继续按每日四个原节点去重，刷新或重启不会重复发送。自动续跑仍按原节点和 3 分钟宽限；开始机会与发送后最多 180 秒的确认等待分别计时，不能将前者理解为端到端耗时上限。
- 无待自动续跑的任务时按节点保活；待用户选择、已取消或明确手动处理的任务不阻挡 Keeper 按原条件保活。已有有效窗口则跳过保活，额度耗尽会阻止发送。保活的计划判断与发送前任务检查使用同一组可忽略暂停事件，并再次核对当前选择；出现新的未忽略暂停时仍会取消本轮保活。
- 有真实额度错误证据且仍未恢复运行的任务，默认全部选中；已确认自然恢复时自动继续，只有新鲜、同账户的连续读数明确证明额度提前恢复时才提醒用户选择。缺少恢复采样不生成询问，保留正常计划和发送前核实。正常完成且额度恰好为 100% 不算撞墙。
- 用户自行继续、终止或任务状态变化后会重新检查，防止重复续跑。
- 可选择待续任务、设置每个任务的固定内容，或读取该任务在 Codex 中已保存的输入框文字。草稿为空时发送“继续”，保留原草稿，仅发送文字，无法可靠读取的格式报错。
- 设置中的“项目可能变化时附加检查提醒”默认开启：项目文件记录变化或无法核对时，在选定内容前单独附加“Codex 额度已恢复，期间项目文件可能发生了变化。请先核对当前任务涉及的项目文件和进度，再继续该任务。”，与选定内容之间留一个空行；关闭后只发送选定内容。提醒不代表已经确认暂停期间有文件变化。
- “取消下一次自动继续”二次确认后仅取消当前这些额度停止事件；未来再次撞墙仍默认续跑。
- 每个任务右上角的删除按钮经二次确认后“忽略本轮”，保存成功才从任务列表隐藏，保留 Codex 原任务与执行记录。忽略按当前暂停事件保存，重启仍有效；用户手动继续后再次额度暂停会形成新事件，仍正常参与续跑。
- 每日开始时间之前的 5 小时属于锚点保护区；实际决策见 `Core/DecisionEngine.swift`。
- 连续观测的自然恢复识别核对预期恢复时间前后 90 秒内的同账户读数。错过该区间时，仍可使用已确认额度停止事件中保存的恢复时间：同账户、该时间已到且实时额度恢复后允许续跑，不依赖相邻两次采样。恢复事实在本次决策前处理，只适用于读数采集前发生且账户已绑定的暂停；旧恢复不能授权新暂停。缺少恢复时间时保留正常计划节点核实，不因此要求用户选择。该补偿不覆盖明确的按计划等待选择、取消和锚点保护；账户不明或变化、额度仍耗尽均不放行。发送前继续核对同一停止事件、任务状态与重复尝试记录。
- 恢复提醒要求同账户实时读数新鲜、额度可用、所需窗口完整，且采样时间严格晚于任务的额度停止时间。停止前仍新鲜的 97% 等读数不能证明停止后恢复。
- 明确提前恢复时使用默认“询问”策略：为同一次额度暂停保存提醒，提供“现在继续”“按计划继续”“取消本次”。未选择只阻止提前发送；之后确认正常恢复时清除未响应提醒、保存状态并进入自动续跑，不用再次选择。明确的取消、取消选中、按计划等待、已响应选择和执行开关不会被覆盖。选择“按计划继续”后在下一可行节点尝试续跑，不能用预测代替发送前确认。各任务独立判断，另一任务的提醒或账户不匹配不阻挡已符合续跑条件的任务。点击通知只打开当前任务列表，不直接发送消息。
- 不再依据用户活动启动十分钟取消期限；旧版保存的提醒阶段和期限仍可读取，但期限不再自动取消续跑。已明确取消的暂停事件保持取消。用户选择“现在继续”后先保存已响应状态，再执行现有预检；预检失败需用户重试，不会在下一节点自行重发。系统通知不可用时仍保留任务入口。
- 任务 rollout 仅接收 `codex` 额度或无 ID 的旧格式，其他限额类别的空窗口不能覆盖已有普通额度。明确额度停止时若最后任务读数仅为 99%，不猜测耗尽窗口；停止之后、同一已绑定账户的实时 100% 读数可补齐或校正对应停止事件的恢复时间，保存在 `pending-runtime.json` 的 `confirmed` 中。保存的校正优先于重新扫描得到的旧值，恢复后新窗口的 0% 重置时间不能反写旧暂停的恢复时间。重新扫描、断网及重启保留同一事件的证据，新停止事件不继承旧选择。
- 本地任务扫描和决策重算保持每 20 秒；健康闲置时外部额度读取降为每 5 分钟。进入闲置须已有可靠的同账户 app-server 读数、本地扫描和认证可读、窗口状态明确，且没有运行任务、续跑需求、执行或关键刷新。启用自动续跑时，额度暂停任务、未选择提醒和按计划等待均保持 20 秒读取；明确取消的事件或关闭自动续跑不长期占用快速轮询。未知状态或读取错误也使用快速轮询策略，但实际请求仍服从 provider 失败冷却。
- 本地发现新任务、用户输入、任务开始、回复或额度停止后立即请求自动刷新并恢复 20 秒读取；发现延迟受本地 20 秒扫描限制。已知运行任务即使被 20 个更新的 rollout 挤出最近列表仍继续监测；无法读取其记录时保留运行状态并暂停自动操作。5 小时/周额度恢复点、原始及有效保活节点前 2 分钟恢复快速读取；越过未确认的恢复点继续等待真实读数。启动、打开菜单、唤醒、网络、系统时间、日期、时区和相关设置变化，以及本地认证摘要变化会触发刷新。
- 关键事件发生在已开始的查询之后时，合并为一次后续自动读取，完成前不自动发送或为新暂停任务绑定旧账户；查询开始前的活动已经覆盖，不重复读取。手动刷新继续按原规则排队。闲置旧读数可保留下一次条件计划和菜单展示，超过 60 秒不授权执行；发送前始终再确认额度、账户、任务和工作区。执行成功后刷新，执行失败依赖常规轮询，避免模型预检失败造成即时刷新和重发循环。

## 额度连接与流量

- `AppState` 为 `UsageObserver` 和 `ExecutionCoordinator` 注入同一个 `AppServerUsageProvider`；正常读取复用一个额度专用 app-server，不再每次启动进程。
- 每次实际读取仍请求真实 `account/rateLimits/read`，不缓存额度结果；完整一次读取串行化，保留 0% 窗口双读及账户核对。仅当该只读请求报明确的上游连接错误时，在同一个 app-server 内立即重试一次；其他请求和错误不作即时重试。完整 RPC 返回的可重试上游错误保留连接；即时重试和保留连接前均核对认证摘要，变化或读取失败时优先返回账户/认证故障，不保留旧读数或继续该次重试。进程退出、管道中断、RPC 等待超时、无效数据、认证和账户变化仍丢弃连接，能力错误沿用原处理。
- 额度专用进程临时覆盖 `features.plugins=false`、`features.remote_plugin=false`，避免启动时下载无关插件目录。普通续跑连接不使用这组覆盖参数；不修改用户持久配置。
- Keeper 创建的 app-server 保留 `CODEX_INTERNAL_APP_SERVER_REMOTE_CONTROL_DISABLED=1` 子进程环境变量；不修改桌面端的远程控制设置。该内部变量的兼容性需在 Codex CLI 更新后复核。
- 认证文件内容摘要改变时丢弃旧连接；读中改变或认证文件不可读时拒绝该次结果。读取或创建失败后，后台按 20 秒至 5 分钟退避；仅可靠的可重试 RPC 服务错误复用连接，其余故障按上述规则关闭并重建。打开菜单或点击“重新同步”可绕过后台冷却，连续失败的手动重试最短间隔 5 秒；已有查询尚未结束时合并为一次后续读取，即使旧查询成功也会执行这次明确请求。正常令牌刷新也可能触发一次保守报错和重连。
- 仅在有效保活机会内，完整 RPC 返回的可重试连接/服务错误使用共享 30 秒请求准入。特殊预算从有效节点开始，以单调时钟固定计时、最多 10 分钟，不在提前 2 分钟准备时启用，也不会因每次重算而续期；机会暂时消失时停用快速准入但保留原截止，恢复同一节点时仅使用剩余预算，到期回到正常退避。模型发现成功不清除额度读取失败计数，也不能紧接着绕过冷却读取额度。账户、认证、能力、无效数据和真实进程/管道故障继续采用原处理；手动重试独立保留 5 秒节流。
- 保存不同的备用 CLI 路径后，通过同一手动刷新机制立即重试额度读取，并允许新值的一次重试绕过 5 秒手动节流；无效输入不触发重试，之后失败仍保留原退避。日志来源为 `cli_path`。错误恢复窗口保存等价路径时，主动发起一次普通手动重试。已有查询继续完成后再读取，健康连接继续复用；不会重启应用或中断正在保活、续跑的进程。
- 额度读取失败时向 `usage-transitions.jsonl` 写入 `usage_read_failed`、脱敏原因、手动/自动触发来源、请求阶段、冷却状态和单调时钟耗时。`rpc_attempted` 区分本次 Keeper RPC 与未发请求的冷却失败，连接初始化是否发出 RPC 无法确认时省略；该字段不表示 CLI 的上游网络请求次数。同一阶段与分类未变的后台失败不重复记录；旧 rollout 仍只是过期的辅助信息。日志超过 1 MiB 后完整轮换，保留当前文件与最多 3 份备份，不截断 JSONL 行。
- 手动刷新在 `usage-transitions.jsonl` 记录 started/queued/finished，区分 `button` 与 `menu_open` 来源，并记录请求 ID、耗时和结果；额度不变时仍能追踪刷新是否完成。
- 上游连接错误转换为跟随应用语言的提示；工作区路由发现超时单独记录为 `workspace_routing_timeout`，界面提示检查网络或代理后重新同步，不把超时直接归因于代理故障。
- 子进程管道断开返回错误，不让 SIGPIPE 终止 Keeper；应用退出只关闭自身登记的 app-server。关闭子进程以单调时钟计时，正常退出宽限为 1 秒，必要时发送 SIGKILL；不再调用无期限的 `waitUntilExit()`，避免退出通知异常时锁住额度读取和后续自动重试。既有执行确认、重复发送和工作区检查保留。
- 实测方法、结果与限制见 [2026-09-15 流量事故记录](流量异常修复-2026-09-15.md)。正常额度查询仍有流量，短窗口速率不能当作全天用量或代理账单。
- 2026-10-09 只读短测：复用连接后 5 次健康非零额度读取约 17.1 KB/批，冷启动约 0.64 MB。健康闲置的周期查询从每小时 180 批降到 12 批，查询部分减少约 93.3%，按该样本约少 2.87 MB/小时；若一天四个故障节点额外增加 40–60 批，按健康样本约增加 0.68–1.03 MB。故障响应与 CLI 内部重试可能不同，这些是条件估算，不是全天账单上限。优化构建中的本地日程及轮询判断约 0.10/0.16 ms/次；尚未测量新版安装后的长期 CPU、内存与 24 小时流量。

## 执行通道与证据

- 保活：`Core/PingEngine.swift` 使用 PTY 启动交互式 Codex，隔离 home / work 位于 `~/Library/Application Support/CodexKeeper/ping/`。隔离配置关闭 `features.daemon_auto_start`，使用自定义 `keeper_http` provider，设置 `supports_websockets=false`、`requires_openai_auth=true` 和 `wire_api=responses`，沿用 ChatGPT 登录及默认端点，省去 WebSocket 启动重试；不修改用户配置、共享服务或续跑通道。共享后台服务不可用或功能不兼容时允许 CLI 本地运行，不等待交互式启动或重启选择。
- 保活模型固定为 `gpt-6-luna`；通过官方 `model/list` 在线发现，支持分页。优先使用支持的 low 推理强度，否则使用模型声明的默认值；查不到时暂停保活并冷却 5 分钟，不切换到其他模型。只有在线发现已经成功、之后额度预检失败，且同一连接、认证摘要与 CLI 路径仍一致时，才可复用最多 5 分钟的发现结果；健康轮次仍在线发现，额度读取成功会清除此缓存。模型确认后始终重新读取额度、账户并检查计划节点。续跑继续继承原任务模型。
- 保活配置生成必须使用 TOML 可接受的字符串转义，不能将路径中的 `/` 写成 `\/`。启动失败和窗口确认超时分别报告。
- 保活成功需要本次隔离任务的 OK 完成记录，以及同一账户新 5 小时窗口的真实确认；进程启动或回复 OK 本身不代表成功。
- 单次保活等待目标为 180 秒；本次隔离任务已收到 OK 并确认完成后，连接结束、超时或明确的暂时服务错误只重试额度核实，沿用共享 provider 的连接复用和失败冷却，任务进程退出也不会提前终止核实。账户变化、认证或能力错误、无效响应及取消立即停止；持续读失败到期显示“已发送但未确认”，不另起保活请求。90 秒仍未确认时显示菜单栏警示，并为本轮发送一次 macOS 通知。首次运行请求通知权限，未允许时仍保留菜单警示；前台也可展示通知。已经发出的额度查询可能使最终返回略晚于目标时间，到期不再发起新查询。
- `execution-events.jsonl` 的保活 `diagnostic` 记录包含实际耗时、提醒/截止阈值、任务与轮次 ID、回复/完成/窗口状态，以及精确匹配本次任务、轮次和时间的重试证据。成功记录新增版本化窗口来源：发送前后账户、原节点、实际重置、计划开始时间及时区；读取时验证窗口时刻与确认时间，再用于下一节点的有限顺延。旧记录仍用于展示确认结果，但不授权顺延；确认列表只在启动和成功后重载。额度核实失败时，`quotaReadFailure` 仅记录请求阶段、可确认的 RPC 尝试状态、冷却、耗时和脱敏分类。仅在有明确证据时区分请求超时、连接、代理和服务响应异常；无证据标未知，不记录原始错误、终端、请求头或令牌。用户提示区分未收到回复与已收到 OK 但窗口未确认；成功或结束时清除中途警示。
- 续跑：优先通过桌面 IPC 找到原写入者并发送 `thread-follower-start-turn`；没有写入者时才使用独立 app-server。发送结果不明确时不切换通道重发。
- 独立 app-server 续跑的 `thread/resume` 使用 `excludeTurns=true`，只向 Keeper 返回任务元数据和实时状态；历史上下文仍由 Codex 恢复，原模型、权限和工作目录不覆盖。会话历史总量不再直接占用 Keeper 的 JSONL 响应缓冲，但 Codex 自身恢复大任务的耗时和内存限制仍存在。
- `AppServerClient` 的 JSONL 读取仍保留 8 MiB 缓冲上限，只扫描新读入的字节寻找行尾；超限单独报告“Codex 返回的数据超过读取上限，已停止本次操作”，诊断为 `response_too_large`，不自动重试，不再混同为格式无法识别。
- 续跑发送与启动确认按任务独立处理；收到准确关联本轮的首个真实模型响应即记为“已继续”，释放启动等待，让任务正常运行，不等待整个任务结束。发送回执、空占位和单纯的 started 不算模型响应。独立 app-server 已接手的任务保留通道至真正结束；退出 Keeper 前明确列出受影响的任务，桌面端原任务不会因停止监听而中断。
- 按 RPC、任务及 turn ID 关联迟到回执、模型活动和结束记录；同一事件只有一个消费方。发送结果不明时保持“确认中”并锁定内容，不能自动换通道或重发。长时间未确认时主时间恢复下一计划，任务入口仍保留确认状态。模型响应后再次遇到真实额度停止，作为下一轮正常处理；可重试中的服务错误不能伪造新暂停。需要授权或输入时不代替用户批准。
- `resume-attempts.json` 保存版本化尝试键和逐任务操作记录，发送内容前原子保存意图，保存失败暂停新的发送。进程重启保留结果不明任务的保护与后续核实，兼容旧尝试记录；不要为测试清空。

## UI 约定

- 菜单栏图标与动作一致：保活 `waveform.path.ecg`，续跑 `paperplane`，额度重置 `arrow.clockwise.circle.fill`。
- 异常 `exclamationmark.circle`，停用 `pause.circle`，同步 `arrow.triangle.2.circlepath`；悬停显示动作与时间。后台同步或暂时连接失败仍有有效计划时保留对应动作图标和时间，不因旧续跑错误常驻感叹号。
- 图标和时间下沿用 3 pt 额度条显示 5 小时剩余额度，不增加状态按钮宽度和高度。有额度条时，图标与时间由同一个原生按钮在额度条上方的内容区居中，不对标题单独偏移基线；额度条贴按钮底边绘制。缺少读数或停用时恢复原生内容位置。两端对齐原生按钮的图标和标题内容边界，随标题长度调整，保留按钮两侧留白。按菜单四舍五入后的百分比配色：11–100% 使用系统主题强调色，0–10% 红色；0% 仅显示淡红色空槽，缺少 5 小时读数或停用时隐藏。使用菜单已有的有效读数，同步期间保留上次结果，不增加查询；悬停和辅助功能标签包含准确的剩余百分比。
- 主时间突出下一步，数字使用系统 Rounded Semibold 字体，不强制等宽；动作和其他文字保持原有字体。非今天的日期放在时间左侧，明天简写“明天”。无可自动续跑任务的计划外窗口显示当前实际额度重置时间；存在续跑计划时显示对应动作时间。
- 有提前恢复提醒、且无其他已获准续跑的任务时，主时间按实际保活计划显示“保持活动”；计划外窗口仍显示真实额度重置时间，暂停任务和顶部提醒保留。选择“按计划继续”后显示对应时间的“自动继续”和续跑图标。未知窗口活动状态不覆盖已获准的有效续跑计划，也不凭空显示窗口详情。菜单展开后，提醒独立放在最顶部，点击进入任务选择；与错误区域并存，不混在时间、任务行或底部说明中。任务窗口和系统通知统一说明“额度提前恢复，可选择现在继续；确认正常恢复后会自动继续。”，同步失败本身不生成恢复方式选择。
- 右上角仅在存在有效窗口时显示计划内 / 计划外；没有窗口时留空。
- 时间轴整体左对齐，各节点内部居中；保留同账户的有效历史和下一动作，只有一个历史入口时也可显示。保活计划中，当前已有有效窗口但没有对应的 Keeper 成功记录和重置证据时，窗口起点显示“窗口开始”，使用中性圆点；匹配成功记录时显示“已保活”或“已继续”。窗口起点按接口的下次重置时间减窗口长度推算，首次读取到满额窗口本身不证明刚发生过重置。同账户后续新鲜官方读数确认较晚的真实窗口时，正常到期使用上一窗口的期限，旧窗口尚未到期就被新窗口替换时使用新窗口起点，标为“已重置”；忽略三分钟以内的时间修正、倒退的窗口起点及窗口长度变化。被提前替换窗口的旧期限不再补成重置事件。既有窗口历史在取得新鲜读数后也可补认此前漏标的提前重置，接口未提供重置原因。续跑计划的未确认窗口起点仍显示“开始”，未知或未开启的窗口不推算起点。原时间线不足三个节点时，向前补当前每日锚点周期内最近的同账户成功记录或实际观察到的有效额度窗口；观察历史保存于 `menu-history.json`，应用重启后在账户、设置、时区和计划周期一致且取得新鲜额度读数时恢复，仅用于展示。已有三个或四个节点保持原样，证据不足时保留原数量；旧版额度日志没有账户归属，不自动据此补回历史。重置须由后续同账户新鲜读数中的有效新窗口验证，预测时间经过本身不算真实事件；接近当前起点或重复确认的节点合并，不影响原有未来动作和重置合并。打开应用的时间不充当窗口起点，晚间锚点周期可跨午夜。观察历史在账户、计划、时区、周期或致命同步错误变化时清除不适用缓存。保活期间保留开始时的时间线和任务；续跑启动完成或短暂确认期结束后显示下一计划，任务确认与历史另行保留。历史续跑节点可点击查看对应批次记录，悬浮使用主题色；“已继续”表示本次启动已确认，不宣称任务仍在运行或已经完成。无账户的旧成功记录不用于历史补充，新续跑记录保存发送前预检验证过的账户。
- 额度使用两行进度条；显示值四舍五入为 0% 时绘制空底轨，非零值用自定义 `ProgressViewStyle` 绘制系统强调色的胶囊条，避免菜单未高亮时变灰；保持原有行高。菜单关闭期间只更新最新读数，保留每条额度上次可见的条长；再次打开并实际可见一帧后，仅对填充宽度做 0.5 秒先快后慢（easeOut）的缓动到最新值，百分比文字始终显示最新读数。非零填充的最小宽度为底轨高度，极小额度显示为圆点；0% 仍为空底轨，数字始终使用实际百分比。首次显示、读数未变化、账户改变或额度行消失后重现时直接呈现当前值；归零与恢复保留同一视图以连续过渡，开启系统“减少动态效果”时不播放动画。打开期间的新读数也平滑更新；关闭菜单取消尚未开始的动画回调。条长历史仅用于展示，不参与额度或执行判断。顶部红色条显示当前额度读取或任务扫描错误。额度与执行判断仍要求 60 秒内的真实读数，原采集时间不延长；菜单单独保留最近有效的时间、额度与时间线，后台刷新或临时失败不会清空内容，提示统一为“上次更新”并显示原采集时间，新读数到达后直接更新。账户、配置、任务选择、日期或时区变化，以及认证、兼容性和任务扫描错误会清除不适用的展示缓存；没有历史有效信息时，空闲显示“待同步”、正在查询显示“正在同步”，读失败说明会自动重试。缓存不参与执行判断，当前错误、恢复提醒和执行警示每次重新叠加。后台成功读取会清除当前读取错误；原续跑失败保留在对应任务详情，保活失败及正在执行的 90 秒等待警示沿用各自的展示规则。只有新鲜、可靠且非空的账户读取与已知绑定明确不符时才能判断账户变化；查询失败、身份缺失或关键刷新中不能推断账户已改变。真实换账户时隔离旧账户任务、选择与记录，切回可恢复。刷新图标位于时间区动作文字右侧；同步中显示进度，点击立即显示正在刷新或排队提示，完成后显示更新时间或失败提示，后续后台刷新恢复显示原读数的更新时间。菜单复用同一视图，在菜单跟踪期间也更新状态，避免销毁点击中的按钮。
- 续跑来源使用系统材质的圆角提示气泡，长标题最多两行，右侧显示“已继续 0/2”形式的本批次进度，有进度时隐藏右侧箭头；不在大标题或任务名后重复数量。失败或需用户处理的任务汇总与提醒使用红色，其他正常状态沿用原色。外层只显示汇总状态，如“1 个任务发送失败”“1 个任务需到 Codex 手动继续”，原因进入详情查看；发送后回执与响应核实统一显示“确认中”。有自动继续计划时，短小、对称的尾箭头指向下方的继续节点。整行可点击，悬浮时底色、任务名和图标高亮。已完成批次从时间轴进入，不保留多余的已完成任务入口。“取消下一次自动继续”位于额度上方，设置和退出菜单项均无图标。设置和任务窗口可调整大小，长内容可滚动。
- 设置页“保持活动”按开始时间即时显示四个“计划预览”时间点，跨午夜标注“次日”；重复说明不再常驻。自动续跑与项目检查的补充说明放在对应文字后的信息图标中，开关保持右对齐；悬停可看短提示，点击可固定查看触发条件及实际添加的提醒文字；计划预览与必要错误仍直接显示。默认发送内容为两项单选：默认文本随应用语言变化且不可编辑；自定义内容在弹窗编辑，设置页仅显示可点击的单行摘要。任务窗口编辑器仍为单层边框。
- 任务窗口标题为“自动继续任务”，使用紧凑任务列表：标题在上，当前状态与原生发送内容下拉框在下，开关位于删除按钮旁。标题与编辑区使用 14pt 系统字体，状态与下拉框使用 13pt，列表外边距 20pt、任务行纵向内边距 12pt。发送内容有三项：默认发送随语言变化的“继续”、自定义内容、使用 Codex 输入框内容；仅自定义显示编辑器，切换模式保留已保存的自定义文字。旧的任务级固定内容和草稿模式保持原选择；没有任务级内容和明确模式时使用默认“继续”。草稿只发送已保存的文字，不含附件，空白时发送“继续”；原草稿会保留。历史时间点只在悬浮时高亮，点击不保留选中状态；历史弹窗只读，不显示删除、开关、重试、打开 Codex 或内容编辑，打开历史不改变手动提醒已读状态。
- 任务详情合并状态和必要原因；已继续只显示真实响应时间与“已继续”，不叠加运行中或本轮结束。失败可提供“立即重试”，自动计划用文字说明，不提供无作用的重复按钮；已发送内容通过禁用编辑器表达锁定，不再增加锁定文案。续跑在首次模型响应前停止且需用户处理时，大时间区域保持“需要手动继续”，详情显示“发送失败，请到 Codex 手动继续”，提供“打开 Codex”；已确认模型响应的记录保留已继续事实。打开真实详情窗口后仅将已停止的手动提醒标记已读，外层恢复正常计划，历史记录和防重发保护保留。
- “开机自启”对应 macOS 登录项。仅系统返回需要批准时显示“请在‘系统设置 → 通用 → 登录项’中允许 Codex Keeper 登录时打开”；普通启用流程无需额外确认。
- 版本入口及更新提示保持在菜单底部；软件更新和问题反馈在关于页处理，具体机制见“关于、更新与反馈”。
- 启用 Keeper 是总执行开关，停用显示“已停用”；旧 executionEnabled 已退役。自动续跑偏好独立保留。

## 代码地图与数据

- `App/`：生命周期、状态汇总、系统事件、菜单及窗口。
- `Core/`：日程、决策、展示模型、执行协调、尝试记录、保活与续跑；`ResumeState.swift` 定义逐任务续跑事实与模型活动证据；`UsagePollingPolicy.swift` 负责闲置判定、提前唤醒和本地活动刷新；`AppUpdateService.swift` 负责应用更新检查和提醒，`FeedbackSupport.swift` 生成反馈链接。
- `Codex/`：只读额度接口、桌面 IPC、任务扫描、额度错误判定、草稿读取。
- `UI/`：菜单摘要、任务编辑、设置、引导及关于页。
- `Tests/main.swift`、`PollingTests.swift`、`ResumeStateTests.swift`：回归检查；`Probes/`：早期探针与原生界面示例。
- `~/Library/Application Support/CodexKeeper/`：`execution-events.jsonl`、`resume-attempts.json`、`usage-transitions.jsonl`、`pending-runtime.json`、`menu-history.json`。这些运行数据独立于源码位置，搬迁不改变它们。
- 执行日志中的 started 只表示开始尝试，confirmed 才是确认成功。
- `pending-runtime.json` 按账户保存暂停、选择、本轮忽略及手动提醒已读状态；与 `resume-attempts.json` 的持久化操作事实配合防重发，不能把清理历史当成恢复故障的办法。

## 已知边界与历史资料

- 官方额外重置的精确事件时刻没有进入当前读取的数据，检测到额度归零的时刻不能当成官方操作时刻。
- 未开启周期时，接口可能返回随查询时间滚动的重置值。5 小时窗口已通过两次读取判断；周窗口的同类显示仍需单独核实。
- 回归通过不等于完整长期稳定性验收；真实执行结果以运行日志为准。最近一次流量修复的验证结果见上述事故记录。
- 2026-10-14 的排查已确认恢复选择误判、短重试预算丢失和无账户旧读数导致假账户变化的逻辑问题；上游 RPC 间歇连接失败的底层原因仍未证实。本轮改善重试和状态恢复，不保证网络或服务从此不再报错。
- `.build/` 是被 Git 忽略的本地构建与临时验证目录；现役源码以项目根目录为准，旧副本不参与构建或安装。
- 原始设计见 [V1 归档](archive/design-v1.md)，只保留设计背景，不作为当前实现规范。
